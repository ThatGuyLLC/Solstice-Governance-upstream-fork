## 4.1 Community Reporting and Disclosure

**Every admitted Orchestrator files a Quarterly Community Report, from the beginning of their first quarter of operation, using the template in [§4.2](#42-quarterly-report-template). Failure to file is a removal trigger and forfeits re-admission for the following quarter.**

Per [§3.1, Policy 9](03-orchestrator-operational-guidelines.md#31-policies), the report covers claims and reward reception; the fields themselves are fixed by the template.

**How to file.**

1. Copy [`quarterly-reports/_TEMPLATE.md`](quarterly-reports/_TEMPLATE.md) to `quarterly-reports/<YYYY-Qn>-<orchestrator>.md`.
2. Fill in every section. Figures marked *(from indexer)* are generated by the versioned reference indexer; pick up the latest figures from the indexer version in §1 of the report. If you do not have a value for a figure — for example, in your first report — leave that field blank.
3. Open a pull request with the completed file and reference it in the quarter's reporting issue (template: quarterly report). `TODO(owners):` who opens that issue and who merges the report pull request.
4. Filing deadline: within **7 days after the verification window closes** (after values bind — posting is 3 days then verification 7 days). The reported FPV must match the **bound** value (the `PostVolume` figure, or the `VolumeCorrected` figure if SRA corrected it in-window). A **zero quarter** (no `PostVolume`, because the contract rejects zero) reports bound value 0 with `no message (zero quarter)` and the indexer run as evidence.
5. On merge, the report is listed in [Section 5, Quarterly Reports](05-quarterly-reports.md).

**If a report is late or incomplete,** SRA Governance opens a public issue and the Orchestrator has the standard response window (7 days) to remedy it before the removal trigger in [§4.4.3](#443-verification-and-removal) is considered. FIP-0118 makes failure to file a removal trigger and forfeits re-admission for the following quarter. The 7-day window is this repository's response step. A later return, if the Safes admit one, is a fresh `AddOrchestrator` with a fresh application, and it is not available in the forfeited quarter ([§2.3.2](02-solstice-program-governance.md#232--remove-an-orchestrator-removeorchestrator)).

**Objecting to a filed report.** Anyone may object to a filed report by opening an issue in this repository, with the orchestrator, the quarter, the figure or statement disputed, and the evidence. There is no standing requirement. Timing decides the remedy:

- **Inside the verification window**, a well-founded objection to a posted figure is an input to the quarterly recomputation and can still be corrected by `CorrectVolume` ([§2.3.4](02-solstice-program-governance.md#234--quarterly-fpv-verification--correction-correctvolume)).
- **After the window closes**, bound values are final. The objection is then a verification trigger under [§4.4.4](#444-what-triggers-a-verification), and the remedy is audit or removal, with no clawback.

An objection to a report's completeness or disclosures, rather than its figures, is not time-bound and is handled under the late-or-incomplete step above. SRA Governance responds within the standard window (7 days).

## 4.2 Quarterly report template

> The report template and example below are repository content. Changing them is a Change-Log action: open an issue, propose the edit by pull request, and record it in the Change Log — not an ad-hoc edit.

The fillable template lives at [`quarterly-reports/_TEMPLATE.md`](quarterly-reports/_TEMPLATE.md). **That file is the single source of truth**; this section states what it must contain and where each figure comes from, so the two cannot drift.

**Required sections.**

| # | Section | What it must carry |
| :-- | :-- | :-- |
| 1 | Orchestrator identification and rewards received | Orchestrator name, registered wallet address, quarter covered, date submitted, and the reference-indexer version used to produce the figures. |
| 2 | Financial performance | The `FPV_i(Q)` headline; the admitted-stablecoin component (USD at face value); the per-pricing-period FIL conversion working (one row per qualifying print); the parameters in effect for Q; the FPV total in both atto-USD and human-readable USD with its `PostVolume` / `VolumeCorrected` transaction reference **or** `no message (zero quarter)` plus indexer evidence; booked revenue by customer segment; and pipeline and sales commentary. |
| 3 | Use of block rewards | Total block rewards received, on-chain disbursements from the Orchestrator wallet, data onboarded (active), storage providers engaged, and a spend-category breakdown. |
| 4 | Retrospective | What worked, what didn't, key learnings, and any other context. |
| 5 | Next quarter outlook | High-level plan and focus areas, and anticipated changes to strategy, spend, or team. |

Section 6 of the template, a signed attestation that the report is not materially false or misleading, is proposed. `TODO(owners): approve` before it is required. It is not a FIP requirement.

**Where the numbers come from.** Every field marked *(from indexer)* is produced by the versioned reference indexer rather than computed manually, so any observer re-running the same indexer version over the same public settlement events reaches the same result. Two constraints are hard: the FPV total **must match** the bound value for that quarter (cite the `PostVolume` message, or the `VolumeCorrected` event when a correction bound; for a zero quarter with no `PostVolume`, cite `no message (zero quarter)` and the indexer run), and the parameters block **must** print `MIN_LOT(Q)`, because it is derived off-chain and stored nowhere else.

**This is disclosure, not scoring.** The report records what happened and how the figures were derived. No field in it is a target or a pass/fail threshold; the only mechanical test in the program is the volume gate fixed by FIP-0118.

## 4.4 Declaration, verification and escalation

### 4.4.1 Two verification duties

These are different duties. Neither is a pre-clearance of individual deals.

**(a) Quarterly recomputation (SRA Governance, every quarter).** FIP-0118 §2.2 makes SRA Governance responsible for supplying the publicly recomputable value before the verification window closes. Each quarter, SRA Governance recomputes every admitted Orchestrator's `FPV_i(Q)` from public settlement events and registry state, publishes that recomputation, and follows [§2.3.4](02-solstice-program-governance.md#234--quarterly-fpv-verification--correction-correctvolume) where a posted figure differs or an Orchestrator did not post. This duty runs whether or not anyone has opened a dispute. The normative algorithm is the FIP text pinned in the [README](../README.md).

**(b) Exception-based audit of a business relationship.** Declarations of client relationships are accepted by default. An audit starts when a trigger in [§4.4.4](#444-what-triggers-a-verification) fires. A false binding surfaces when the registrant does not serve the client, on the evidence in [§4.4.2](#442-dispute-resolution-for-contested-bindings). This repository does not use an undefined KPI or SLA as a verification standard.

FIP-0118 fixes the consequence of a misreport discovered after binding:

> "There is no retroactive clawback: a misreport discovered after binding is grounds for audit or removal (Section 4)."

### 4.4.2 Dispute resolution for contested bindings

1. The contesting party opens an issue in this repository identifying the pair and its claim.
2. SRA Governance requests evidence of the client relationship from both parties. Acceptable evidence, in increasing strength: business records showing the engagement; client confirmation through a verifiable channel; a signed client attestation (a message signed by the payer wallet naming the orchestrator).
3. Resolution target timeline: 7 days. The outcome (reassignment, removal, or no action) is recorded on the issue with a written reason. A reassignment uses [§2.3.11](02-solstice-program-governance.md#2311--reassign-a-binding-reassignbinding), including when `inherit = true` applies. A removal uses [§2.3.2](02-solstice-program-governance.md#232--remove-an-orchestrator-removeorchestrator). The call executes on-chain when the second SRA Safe approves. Registry actions are not held and not cancellable after that approval.

A dispute that asks for a `CorrectVolume` in the open verification window is filed by day 4 of that window. `TODO(owners):` an independent appeal reviewer. This repository does not name one.

**Evidence handling.** Pairs are public on chain once registered. The declaration points at that record (Policy 6). The worked example above is fabricated. It shows segments and anonymised deal descriptions. It does not publish named clients. Business records and client confirmations filed on a public issue can be redacted so that a person is not named, with the unredacted record described on the issue. `TODO(owners):` a legal review of data protection, pending counsel, and whether a private submission to both Safes is adopted. This repository does not open a private channel.

A figure still inside the verification window is an input to the quarterly recomputation and to `CorrectVolume`. It is not a substitute for duty (a) above.

A contested `CorrectVolume` follows the same evidence process. Per the FIP, bound values are final, so the appeal outcome can only affect later quarters:

> "Binding: whatever each value is when the window closes binds, and bound values are final for the quarter."

### 4.4.3 Verification and removal

The exception audit in §4.4.1(b) is never pre-clearance. A scheduled audit of individual deals would rebuild the review pipeline Solstice deprecates. That audit begins when a trigger fires: a public-data anomaly, a community report filed as an issue, or a contested binding escalated from the dispute process ([4.4.2](#442-dispute-resolution-for-contested-bindings)). It does not replace the quarterly recomputation in §4.4.1(a).

**Grounds for removal:**

- Failure to file the quarterly report. The FIP makes this a removal trigger and forfeits re-admission for the following quarter.
- Misreported FPV. The figure is recomputable from public events. Inside the verification window the remedy is `CorrectVolume`. After binding, the FIP's remedy is audit or removal, with no clawback.
- A pattern of wrongful claims (FIP-0118, Security Considerations).
- Wash trading and self-dealing. This list entry is repository policy. FIP-0118 lines 145–148 at the pin:

```
misreported figure is detectable and correctable, while distinguishing
genuine demand from self-dealing is an off-chain judgment assigned to
SRA Governance, which can remove an Orchestrator (Section
4.2).
```

The FIP does not require this repository to use the words "wash trading" as a named ground. The issue records the settlement path (payer, operator, rails, and epochs) and why the path is circular or self-dealt, using the evidence list in [§4.4.2](#442-dispute-resolution-for-contested-bindings). The Safes decide. A threshold is not set.
- Materially false or misleading report content. Proposed repository policy, not a FIP requirement, and not in force. `TODO(owners): approve`. The evidence is the report file and the public record it contradicts. The attestation line in the report template is part of the same proposal.

**Terms.**

- **Wrongful claim.** A `RegisterPairs` binding that the dispute process finds the registrant does not serve for that client. The FIP uses "a claim adjudicated wrongful" and names a pattern of wrongful claims as removal ground. While the quarter runs, and the displaced binding's application epoch is in the current quarter or later, the remedy is `ReassignBinding` with `inherit = true` ([§2.3.11](02-solstice-program-governance.md#2311--reassign-a-binding-reassignbinding)).
- **Wash trading and self-dealing.** Repository name for the off-chain judgment FIP-0118 assigns to SRA Governance: distinguishing genuine client demand from circular payments between colluding parties. Listed as a removal ground above. That listing is repository policy.

The evidence for a relationship is the list in [§4.4.2](#442-dispute-resolution-for-contested-bindings).

- A public-data anomaly surfaced by the quarterly FPV recomputation or by monitoring (volume spikes at quarter or gate boundaries, figures that clear the target by a hair, volume with no matching storage activity). ### 4.4.5 Escalation

1. **Trigger** → run the relevant on-chain checks (see [§3.2](03-orchestrator-operational-guidelines.md#32-orchestrators-tasks-and-actions)); the recomputation is deterministic and public.
2. **Request evidence** if an anomaly holds: open a public issue and request on- and off-chain evidence; the orchestrator answers within the response window (7 days).
3. **Decide:** reassign a binding under [§2.3.11](02-solstice-program-governance.md#2311--reassign-a-binding-reassignbinding), or `RemoveOrchestrator`. Record the written reason.
4. Registry changes bind at once and are recorded in the Change Log (see [§2.3](02-solstice-program-governance.md#23-sra-governance-tier--tasks-and-actions)) and are recorded, with rationale, in the issue.
